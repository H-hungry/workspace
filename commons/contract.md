# 协作契约（contract）

> 本文件是工作台最高规则文件，所有协作者（含其 AI）必须遵守。修改本文件须回执知会全体成员并在日志中登记。

## 1. 目录结构与各区用途

| 区域 | 路径 | 规则 |
|---|---|---|
| 公共区 | `commons/` | 人人可读；修改须回执知会全体成员 |
| 成员区 | `members/<成员>/` | 成员本人的工作范围；他人只可向其 `inbox/` 新增文件 |
| 日志区 | `logs/` | 只追加，不修改，不删除 |

成员区内五个组成部分：

| 目录/文件 | 用途 |
|---|---|
| `inbox/` | 收到的任务、回执、异议（他人投递的唯一入口） |
| `drafts/` | AI 生成、待人审核的草稿（未生效） |
| `deliverables/` | 人工审核通过后的生效唯一版本 |
| `archive/` | 历史版本、已闭环任务、作废文件 |
| `workspace.md` | 本人总目标与分步计划进度 |

## 2. 文件命名规范

| 文件类型 | 命名格式 | 示例 |
|---|---|---|
| 任务/异议投递 | `YYYYMMDD-任务名.md` | `20260901-活动落地页设计方案.md` |
| 回执 | `YYYYMMDD-re-任务名.md` | `20260901-re-活动落地页设计方案.md` |
| 草稿/产出 | `任务名-vN.md`（版本号只属于产出，投递文件不携带） | `活动落地页设计方案-v1.md` |
| 共识文件 | `NNN-主题.md`（编号递增，不复用） | `001-项目共识.md` |

## 3. 文件头元信息（跨区投递文件必填）

```markdown
<!--
type: task | receipt | objection | decision
from: A | to: B
status: pending | accepted | rejected | done
priority: high | normal   （仅 task 类必填，缺省视为 normal）
date: YYYY-MM-DD
依据: commons/consensus/001-项目共识.md#L12   （可选，注明依据的共识条目）
上游: members/B/inbox/20260901-xxx.md        （回执/异议必填，指向原任务）
-->
```

## 4. 状态流转

任务状态：`pending（待处理）→ accepted（接单）/ rejected（退回）→ done（闭环）`

- 收件人处理任务后**不修改原任务文件**，状态变更通过向对方 inbox 投递回执表达
- 已闭环（done）的任务及回执由收件人移入自己的 `archive/`

产出流转：`drafts/（草稿）→【人工审核】→ deliverables/（生效唯一版本）→ 迭代出新版时，旧版移入 archive/`

## 5. 禁区（红线）

1. 不得修改他人成员区内任何文件；跨区协作只能向对方 `inbox/` **新增**投递文件
2. 草稿未经对应成员**人工审核**，不得转入 `deliverables/`（human in the loop 铁律）
3. 公共区（`commons/`）修改必须在回执中知会全体成员，并在日志中登记
4. 不得删除任何历史文件；作废只能移入 `archive/`
5. 关键协作信息必须以文件形式流转，禁止仅靠会外口头/聊天传递

## 6. 双向引用规范（白盒化）

- **正向**：产出文件头注明 `依据:`（引用的共识/契约条目）与 `上游:`（来源任务）
- **反向**：修改共识文件条目前，先全文检索引用了该条目的产出文件，评估影响并在回执中说明

## 7. 会话与 Git 规则

1. 开工第一步永远是 `git pull` 拉取最新版本
2. 每处理一个新任务，**新开一个 AI 会话**（上下文 = 公共区 + 自己 inbox + workspace，不依赖会话记忆）
3. 一个动作一个 commit，commit message 格式：`[A→B] 投递任务: xxx`、`[B] 交付产出: xxx v1`、`[B] 回执: 已完成 xxx`
4. 完工即 push，不留未推送的本地提交

## 8. 人工裁决点（human in the loop）

AI 承担流程中全部内容加工环节（起草、分析、建议）。以下决定产生对外效力——生效版本对外代表成员本人的正式产出，任务闭环代表对上游承诺的兑现——**必须由人做出**，称为人工裁决点：

1. **审核**：草稿 → 生效（产出成员本人裁决）
2. **验收**：产出 → 任务闭环（任务发起方裁决）

## 9. 多任务与优先级

1. 任务文件头可标注 `priority: high | normal`，缺省视为 normal
2. inbox 处理顺序：high 优先于 normal；同优先级按投递日期先进先出
3. 同一成员同一时刻只应有一个"正在做"的任务（见 workspace.md 当前状态视图）；多任务通过分批处理消化，不得并行交错

## 10. 版本管理细则

1. **验收方在回执中要求修改**产出时，才产生新版本（vN+1）；不影响验收结论的小改不升版本
2. 新版本生效时，旧版本从 `deliverables/` 移入 `archive/`，保证 `deliverables/` 内同名任务只保留最新生效版（"生效唯一版本"红线的执行细则）
3. 版本号体现在文件名（`任务名-vN.md`），文件头无需重复标注

## 11. 异议与升级机制

1. 接单方认为任务不合理时，写 `objection` 文件投回发起方 inbox 说明理由；原任务按退回处理（通过回执表达，不修改原任务文件）
2. 发起方收到异议后三选一：
   - **撤回**任务（在日志中登记终态）
   - **补充背景 / 修正要求**后，重新投递新任务文件
   - **分歧源于共识本身**时，修订共识文件（走 §12 流程），使依据成立后重新投递
3. 铁律：**任何投递不允许悬空搁置**——每个任务最终必须到达终态：`done`（闭环）或被撤回

## 12. 契约与共识的修订流程

1. 修订提案以 `decision` 类文件投递至全体成员 inbox，写明：修改什么、为什么、影响哪些文件
2. 全体成员确认无异议后，提案发起方执行修改，并在日志中登记
3. 共识文件编号只增不复用：一般修订在原文件内追加；重大重构则新建 `NNN-` 文件并注明取代关系
4. 修订生效前，按 §6 双向引用规范反向检索受影响的产出文件，在回执中说明影响范围
